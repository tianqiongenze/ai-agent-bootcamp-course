## 一、课程需求分析(SRS - 课程交付侧)

### 1.1 干系人与目标

| 干系人 | 目标 |
|---|---|
| 学员(传统后端/全栈工程师) | 转型 AI Agent 开发工程师,获得**三个可展示作品集 + 一个生产级平台** |
| 讲师(您) | 拿到**开箱即用**的全套授课材料:PPT、讲稿、实验手册、案例代码、考核题库 |
| 教学机构 | 课程可复制、可考核、可迭代(Eval 数据驱动课程改进) |

### 1.2 功能需求(课程交付物清单,FR-C)

| 编号 | 交付物 | 说明 |
|---|---|---|
| FR-C1 | 授课计划(教学日历) | 7 章 → 课时拆分、每讲目标/重点/实验/作业/考核 |
| FR-C2 | 授课 PPT | 每章 1 份(含章节总览),合计 7 份,工业级视觉规范 |
| FR-C3 | 讲师讲稿/教学笔记 | 每讲的讲授要点、板书、提问设计、常见误区 |
| FR-C4 | 实验手册(Lab Guide) | 每章 1-2 个可跟做实验,含验收标准 |
| FR-C5 | 工程代码(Agent Engineering Platform) | 单仓 monorepo,六大演进阶段分支/标签,全链路可测可运行 |
| FR-C6 | 习题/作业/项目评分标准(rubric) | 含面试题库(大纲第七章第四部分) |
| FR-C7 | 考核方案 | 过程考核 + 三大作品集答辩式终审 |
| FR-C8 | 部署与运维材料 | Docker Compose、Runbook、上线检查单 |

### 1.3 非功能需求(NFR-C)

- **可执行性**:每条实验步骤在 macOS(Docker)+ Linux 验证通过;代码含 README,一条命令起环境。
- **可测性**:平台代码 TDD 开发,核心模块行覆盖 ≥80%(测试覆盖率门禁铁律);LLM 调用全部 Provider 抽象,CI 用 Mock Provider 零外部依赖。
- **可移植性**:单机 Docker Compose 验证拓扑,架构设计按多节点可扩展(不降级设计)。
- **迭代性**:Eval 与课程质量数据联动(学员 Agent 任务成功率 → 课程改进)。

## 二、平台工程需求分析(SRS - 软件侧)

### 2.1 平台定位

大纲规定的最终交付:**统一、完整、可展示的 Agent Engineering Platform**,含 20 项能力(LLM Gateway / Prompt / Structured Output / Tool Runtime / MCP / Codebase Agent / Agent Loop / State Machine / Sandbox / Context Manager / Project Memory / Codebase RAG / Multi-Agent / Skill System / Agent Eval Platform / Trace / Replay / 成本统计 / 灰度发布 / Docker Compose 部署 + Runbook)。

### 2.2 功能需求(FR-P,按 DDD 限界上下文分组)

| 限界上下文(BC) | 核心能力(对应大纲章节) |
|---|---|
| BC1 模型网关 Gateway | OpenAI Compatible 统一入口、多模型路由/Fallback、Streaming(SSE)、Structured Output、Prompt 模板版本管理、Token/Cost/Latency 留痕、限流重试(§1) |
| BC2 工具运行时 Tool Runtime | Tool Registry/Schema/发现/版本/启停、JSON Schema+Pydantic 校验、RBAC+风险分级、审计、超时重试降级、MCP Client 接入、CLI(§2) |
| BC3 Agent 编排 Orchestration | Agent Loop(observe→plan→act→observe→finalize)、ReAct/Plan-Execute、State Machine(9 态)+Checkpoint、Sandbox(本地+Docker)、Human-in-the-loop、Codebase Agent 十类工具(§3) |
| BC4 上下文与记忆 Context/Memory | Context Packing/Budget/Compression、Working Memory、短期/长期/项目级记忆、Codebase RAG(AST 分块+Hybrid Search+Rerank+Citation)、Context Debug Report(§4) |
| BC5 多智能体与技能 Multi-Agent/Skill | Supervisor/Planner-Executor/Reviewer 模式、六角色 Agent、任务委托/聚合/仲裁、Skill 生命周期(§5) |
| BC6 评测 Eval | Golden Dataset、14 项指标、Rule/Schema/Snapshot/LLM-as-Judge/Human Eval、回归测试、Trace Analysis、失败样本聚类(§5) |
| BC7 治理与可观测 Governance/Observability | Trace/Replay、四类监控指标与告警、六类版本对象、Feature Flag 灰度、成本治理、Runbook(§6) |

### 2.3 非功能需求(NFR-P,工业级指标)

| 维度 | 指标 |
|---|---|
| 性能 | LLM Gateway P95 代理开销 <50ms(不含模型推理);工具调用审计异步化,P99 <10ms 附加 |
| 可用性 | 无状态服务多副本;PG 主从+自动失败转移演练(单机以 compose 拓扑表达,多节点设计不缺席) |
| 数据 | 关键业务事件(任务状态/审计)at-least-once + 幂等消费(Transaction Outbox) |
| 缓存 | 四级缓存(L1 进程内 → L2 Redis → L3 Prompt/Semantic Cache → Tool Result Cache),命中率可观测 |
| 安全 | API Key 不入库、Secret 环境变量/配置中心、Trace 脱敏、Sandbox 边界、工具白名单、RBAC |
| 一致性 | 并发读-改-写实体(任务/评测)乐观锁 version 列;读己之写场景基线读主库 |

### 2.4 您指定的工业级技术要求如何落位

| 要求 | 平台落位方案(草案) |
|---|---|
| **读写分离** | PostgreSQL 主从(流复制):写=主库,读(报表/Trace 查询/工具目录)走从库路由器;读己之写与强一致基线读回源主库 |
| **GraphQL** | 对外统一 API 采用 GraphQL(strawberry-graphql + FastAPI):任务/Trace/Eval 报告/工具目录/成本报表等查询场景;SSE 流式与 Webhook 保留 REST 端点(GraphQL SSE 作为进阶选学) |
| **Pulsar MQ** | 事件骨干:工具审计事件、LLM 调用留痕、任务状态变更(Outbox 投递)、Eval 批量任务、Trace 异步落库、死信队列;Docker Compose 内 Pulsar standalone |
| **多级缓存** | L1 进程内 LRU → L2 Redis → L3 LLM 语义缓存(精确 hash + 向量语义命中)→ Tool Result Cache;命中率指标 `cache_hit/cache_layer` 透传 |

> 以上四项与大纲原生栈(FastAPI/Redis/PG/向量库)融合,不冲突:它们正是第六章"生产化"的工业级实体化,并作为课程差异化亮点(超越市面 Demo 级课程)。

## 三、总体架构(草案,TOGAF ADM 裁剪)

### 3.1 业务架构(BA)

```
学员旅程:基础调用(LLM API) → 工具治理(Tool/MCP) → 长程任务(Loop/State/Sandbox)
        → 认知增强(Context/Memory/RAG) → 协作与质量(Multi-Agent/Eval) → 生产化(Deploy/Observability)
        → 综合落地(DeerFlow 解析/深度研究/软件工厂/产品化)
```
每个旅程阶段 = 平台一个演进阶段 = 课程一章 = 一个可验收里程碑(TOGAP 阶段门)。

### 3.2 应用架构与 DDD 划分(草案)

```
                     ┌────────────────────────────┐
   Client ─GraphQL─▶ │  API BFF (GraphQL, FastAPI)│─SSE─▶ REST /ws 端点
                     └──────┬─────────────────────┘
        ┌───────────┬───────┼────────┬──────────┬───────────┐
   BC1 Gateway  BC2 Tool    BC3 Agent    BC4 Context   BC5 Multi    BC6 Eval
   (模型路由/   Runtime    (Loop/State/ (Memory/RAG/  (Supervisor/ (Benchmark/
    缓存/留痕)  (注册/校验/  Sandbox/     Compression)  Skills)      Judge/回归)
                权限/MCP)   Checkpoint)        │
        └───────────┴───────┴────────┴──────────┴─────┬─────┘
                                     BC7 治理:Trace/Replay/版本/灰度/成本 (横切)
```
- 聚合根候选:`Tool`、`AgentRun(任务)`、`Skill`、`EvalSuite`、`KnowledgeBase`
- 战术模式:Repository + Domain Event + Outbox;领域事件经 Pulsar 发布

### 3.3 数据架构(草案)

| 存储 | 用途 | 拓扑 |
|---|---|---|
| PostgreSQL | 业务库(工具/任务/评测/版本/审计)+ Outbox | 主从读写分离 |
| Redis | L2 缓存、会话/任务状态热点、限流计数 | 单实例(多节点设计) |
| Milvus/Chroma | 向量检索(Codebase RAG、语义缓存) | 容器单节点 |
| Pulsar | 领域事件、审计流、Eval 任务、DLQ | standalone |
| 对象卷 | Trace 快照/Replay 数据/Checkpoint | 卷挂载 |

### 3.4 技术架构(部署视图,单机 Compose 验证、多机可移植)

```
docker compose:
  api-graphql / api-internal / worker-agent / worker-eval / relay-outbox
  pg-primary ─流复制─▶ pg-replica
  redis / pulsar / milvus(或 chroma) / jaeger(Trace 演示,选配)
```

### 3.5 方法论落位(TDD/SDD/DDD/TOGAF)

| 方法论 | 在本课程工程中的落位 |
|---|---|
| **SDD(Spec-Driven)** | 每阶段先写 spec(需求/接口契约/验收标准)→ plan → tasks → implement;spec 作为教学产物示范 |
| **TDD** | 红-绿-重构;每讲实验含"先写失败测试"环节;CI 覆盖率门禁 ≥80%(核心模块) |
| **DDD** | 上述 7 个限界上下文 + 聚合/领域事件/防腐层(MCP 适配即防腐层实例) |
| **TOGAF** | 架构文档按 BA/DA/AA/TA 四视图 + ADR 决策记录组织;每章=ADM 迭代 |
