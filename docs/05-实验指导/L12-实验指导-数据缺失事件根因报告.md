# 实验 L12：数据缺失事件根因报告（血缘溯源 + 修复审批）

**（实验指导 ｜ 对应学习情境 L12 ｜ 企业站 2 学时 ｜ 实验⑫ ｜ M2 验收周）**

| 项 | 内容 |
|---|---|
| 实验类型 | 综合演练（事件响应） |
| 实验环境 | 课程环境根因 Agent、NebulaGraph 血缘（CRDB 双写兜底）、审批工作流 |
| 分组 | 部门协作（值班工程师/质量治理/记录员） |

## 一、实验目标

1. 【分析】用血缘查询完成一次数据缺失事件的根因定位（双 Agent 协作路径）。
2. 【应用】走完"修复建议→审批→执行→留痕"闭环。
3. 【素养】以"业务总监"能听懂的方式写事故报告（课后费曼题目）。

## 二、环境与准备

- 教师注入场景：售后域 ADS 表某日数据缺失/骤降（注入细节保密，学生只看现象）。
- 材料血缘链提示：`ods → dwd → dws → ads` 各级调度任务与依赖关系（Nebula 查询模板课堂已发）。
- 纪律：根因未定位前**禁止**直接"重跑补数"——先定位再修复是铁律。

## 三、实验步骤

### 步骤 1：现象确认与影响面（20′）

```sql
-- ADS 层按天核对行数，定位缺失窗口
SELECT dt, COUNT(*) FROM ads_cs_sla_day GROUP BY dt ORDER BY dt;
```

记录：缺失窗口、影响指标、疑似上游。

### 步骤 2：血缘溯源（50′）

1. 根因 Agent 发起血缘查询（或手工 Nebula 查询模板），沿 ADS→DWS→DWD→ODS 逐级核对：
   - 各级当日行数
   - 调度任务状态（Pulsar 队列/DLQ 有无死信）
2. 定位断点（示例：某级任务失败 → DLQ 死信 → 下游断供），记录证据链。

✓ 验证点：血缘路径图 + 每级行数对照表；双写兜底（CRDB）数据与 Nebula 结论一致性核对。

### 步骤 3：修复建议与审批（20′）

1. 根因 Agent 生成修复建议（如：回放死信 → 重跑某级任务）。
2. 发起审批工作流：建议内容 + 影响面 + 回滚方案；**必须经另一部门成员审批**后执行。
3. 执行修复，复验 ADS 行数恢复。

✓ 验证点：审批单截图（含审批人与时间戳）+ 修复后行数恢复证据。

### 步骤 4：《根因分析报告》（10′ 起稿，课后完成）

结构：现象→定位过程→根因→修复→防复发（至少 1 条）。语言要求：业务方可读（"上游队列积压死信"要翻译成"数据进不来被拦下了"）。

## 四、常见坑与排障

| 现象 | 原因与处置 |
|---|---|
| 一上来就重跑任务 | 违反铁律：未定位根因的重跑可能重复污染下游 |
| 血缘查不到节点 | 血缘库滞后或未采集该任务；用 CRDB 双写兜底链核对并报告缺口 |
| 修复后又缺数据 | 根因其实在上游注入源未恢复；回到步骤 2 重定位 |
