## 一、实验目标

1. 【应用】设计售后域 4 条质量规则（对应课程标准 LF4 企业任务）。
2. 【理解】体会"规则为主、LLM 为辅"的边界——能用 SQL 判定的绝不请 LLM。
3. 【应用】触发一次全量巡检，逐条解读失败项并定性（真问题/规则误配）。

## 二、环境与准备

- 规则五类（至少覆盖 4 类）：空值率 / 值域 / 新鲜度 / 行数波动 / 唯一性。
- 售后域表：L02 设计、L08 建索引后的 `dwd_cs_ticket_di` 等（若尚未建表，用教师提供的样例表）。
- 提醒：规则 SQL 一律先在沙箱执行验证，再入库生效。

## 三、实验步骤

### 步骤 1：规则设计（50′）

| # | 规则类型 | 规则定义（示例） | SQL 要点 | 阈值与告警级 |
|---|---|---|---|---|
| 1 | 空值率 | 当日工单 `close_time` 空值率 <5% |  |  |
| 2 | 值域 | 处置时长 ∈ [0, 72h]，超出记异常 |  |  |
| 3 | 新鲜度 | `ods_cs_ticket` 数据延迟 ≤T+1 早 8 点 |  |  |
| 4 | 行数波动 | 日行数环比波动 ±30% 内 |  |  |
| 5（选） | 唯一性 | ticket_id 无重复 |  |  |

✓ 验证点：每条规则附"这条规则为什么值钱"一句话（对着真实业务风险说，如"close_time 空值会让 SLA 看板算不出"）。

### 步骤 2：入库与巡检（30′）

```bash
# 规则入库 → 触发全量巡检（命令见质量引擎 README）
make quality-scan
```

✓ 验证点：巡检结果截图；扫描→结果→告警链路各环节证据。

### 步骤 3：失败项解读（20′）

对每个失败项先二分定性：

- **真问题**：数据真的坏了 → 走根因流程预告（L12 预习）。
- **规则误配**：阈值/口径不对 → 修规则并记录修订理由。

✓ 验证点：每个失败项给出定性结论与证据；如全部通过，人为制造 1 处脏数据（教师提供的污染脚本）复测告警。

## 四、常见坑与排障

| 现象 | 原因与处置 |
|---|---|
| 规则 SQL 全表扫描拖垮巡检 | 大表先按分区抽样/限定日期；巡检 SQL 也要讲成本 |
| 波动规则天天误报 | 没排除节假日/大促等自然波动；阈值带业务日历 |
| 用 LLM 判空值率 | 边界错位：可 SQL 判定的用规则，LLM 留给语义类检查 |
