## 一、实验目标

1. 【应用】为本学期自己的改动补 2 个单测，覆盖率门禁（80%）通过（对应课程标准 LF6 企业任务）。
2. 【分析】执行一次 k6 阶梯压测并判读拐点。
3. 【理解】跑一次班级评测集，理解 bootstrap CI 的意义（教授方法学）。

## 二、环境与准备

- 前置：本组学期内合并的 PR 清单（选 2 个核心改动）。
- 工具链：pytest + coverage、k6（教师提供课程集群内压测机）、评测集 CLI。
- 纪律：压测目标限课程命名空间服务；RPS 上限遵守教师发放的配额（容量诚实）。

## 三、实验步骤

### 步骤 1：补单测过门禁（50′）

这步在干什么：先看覆盖率报告找缺口，再为选定改动补 2 条测试并本地跑绿。

```bash
# ① 定位缺口：看覆盖率报告中标红的分支（真实命令，等同 make test）
# 注意：必须从 packages/dap_core 目录起跑；直接在仓库根跑 pytest 会因 rootdir
# 解析错位收集 0 条测试（exit 5）——这是本项目已踩过的坑
cd packages/dap_core
uv run pytest ../../services ../../packages -q -p no:cacheprovider \
  --cov=dap_core --cov-report=term-missing --cov-fail-under=80

# ② 为选定改动编写 2 个测试（建议：1 个正常路径 + 1 个边界/异常路径），如：
uv run pytest tests/test_l15_teamXX.py -v -p no:cacheprovider
```

✓ 验证点：CI 门禁全绿截图（覆盖率 ≥80%；基线以 dap-v2 当前 main 为准——当前 67 测/行覆盖 87%，随演进以 `make test` 实时输出为准，不钉死历史数字）。

### 步骤 2：k6 阶梯压测与拐点判读（40′）

1. 执行教师发放的阶梯脚本（如 20→60→100→140→180 RPS 各 2 分钟；仓库参考脚本 `tests/load/k6_gateway.js`，历史实测产物 `tests/load/k6_summary.json`——其 140RPS 为 70% 缓存混合负载口径，判读以本档实测为准）。
2. 记录各档 P95 时延与错误率：

| 档位 RPS | P95 (ms) | 错误率 |
|---|---|---|
| 20 |  |  |
| 60 |  |  |
| 100 |  |  |
| 140 |  |  |
| 180 |  |  |

3. 判读：拐点在哪一档？依据是什么曲线特征（P95 陡增 / 错误率起跳）？

✓ 验证点：k6 原始输出入库 + 判读结论一段。

### 步骤 3：评测集与 bootstrap CI（20′）

1. 跑班级评测集（held-out；仓库真实脚本 `tests/eval/run_eval.py`，24 题内含 held-out 12），记录准确率与均时延。
2. 用教师脚本对评测对错序列做 bootstrap 重采样（10000 次），输出 95% CI。
3. 回答：为什么"91.7%"必须带着"CI 79.2–100%"一起说？（小样本评测的诚实口径）

## 四、常见坑与排障

| 现象 | 原因与处置 |
|---|---|
| pytest 收集 0 条测试（exit 5） | 从仓库根直接起跑导致 rootdir 解析错位；必须 `cd packages/dap_core` 后按步骤 1 命令执行 |
| 测试全绿但门禁失败 | 覆盖率未达 80%；补测缺口分支而非堆凑数测试 |
| k6 把服务打挂 | 阶梯超配额；降档重跑并记录（这本身是容量诚实素材） |
| CI 准确率 100% 但抽测错 1 题 | 检查评测集是否泄漏进 few_shots；held-out 必须隔离 |
