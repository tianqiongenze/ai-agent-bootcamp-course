## 二、任务描述

某零售集团数据部收到运维部通报：dap-v2 网关上周滚动更新出现短时 502，根因是该组件 readinessProbe 缺失且未配 preStop，旧 Pod 还在接流量就被杀。运维部要求数据部按平台规范重写 dap-gateway 部署清单（Deployment/Service/ConfigMap/Secret/Ingress/探针齐全），先在教学 namespace 验证再上生产，并附一次滚动更新不中断的证明。

## 三、学习目标

1. 【应用】能独立编写 dap-gateway 最小部署清单（以 `deploy/k8s/04-gateway.yaml` 为基准：Deployment＋Service＋ConfigMap＋Secret＋Ingress＋三类探针＋resources），在 `dap-course-g0X` 内 `apply` 成功且 Ingress 路由可达。
2. 【应用】能正确区分并配置 livenessProbe 与 readinessProbe（/healthz、/readyz），并解释设计差异：readyz 检查关键依赖（Redis/DB PING，失败摘流量返 503），healthz 只查进程存活（失败才重启）。
3. 【分析·渗透】能通过"删 Pod／断依赖／坏 Secret"三组故障实验预测并解释集群行为（自愈重建、Endpoints 摘除、挂载失败），用 `kubectl describe`/`kubectl get events` 定位原因。
4. 【应用·渗透】能完成一次安全滚动更新：改镜像 tag→`rollout status` 观察→`rollout undo` 回滚，并用压测/循环 curl 证明业务不中断。
5. 【素养·渗透】践行平台公约：Secret 不入 Git（占位＋CI 注入）、live patch 必回写仓库 yaml、所有验证以命令输出为证（无产物不声称完成）。

## 四、教学重点与难点

### 教学重点

1. 五类核心对象的职责与接线关系：Deployment（副本与滚动）、Service＋Endpoints（稳定访问入口）、ConfigMap/Secret（配置与敏感配置分离）、Ingress（七层路由与 TLS）。
2. 探针三态与优雅关停：startup/liveness/readiness 分工；`terminationGracePeriodSeconds`＋preStop 保证在途请求排空——这正是本次 502 事故的直接解药。

### 教学难点（附突破策略）

1. **readyz vs healthz 的设计辨析**——学生极易把两个探针都指到"查依赖"或都指到"查进程"。
   突破策略：双实验对照法——①正确配置：kill 课程 Redis 依赖→readyz 503→Pod 从 Endpoints 摘除→上游拿到 503 优雅降级、进程不重启；②反面实验：故意把 livenessProbe 指向 /readyz→Redis 抖动→Pod 被 kubelet 反复重启→观察 CrashLoopBackOff。一正一反，肌肉记忆。
2. **Service/Endpoints 与 Ingress 的路由映射**——yaml 都能 apply，但"流量到底走没走通"心里没图。
   突破策略：链路追踪法——`curl -H "Host: gw-g01.dap-course.local" http://10.167.2.175/api/ping` 起，沿 Ingress 规则→Service selector→Endpoints 列表→Pod IP 四跳逐一取证据，画成流量追踪图。

### 6.4 实施（90′）

#### 子步骤 1：填空编写清单（20′）

在填空版基础上补全（关键段示例，其余沿用基准）：

```yaml
# deploy/k8s/04-gateway.yaml（课程填空版·关键段）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: dap-gateway
  namespace: dap-course-g01          # 本组 ns
spec:
  replicas: 2
  template:
    spec:
      containers:
        - name: gateway
          image: registry.local/dap/gateway:course-v1.0
          envFrom:
            - configMapRef: { name: dap-gateway-config }
            - secretRef:    { name: dap-gateway-secret }
          readinessProbe:                 # 摘流量用：查依赖自愈
            httpGet: { path: /readyz,  port: 8000 }
            periodSeconds: 5
            failureThreshold: 2
          livenessProbe:                  # 重启用：只查进程存活
            httpGet: { path: /healthz, port: 8000 }
            periodSeconds: 10
            failureThreshold: 3
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: dap-gateway
  namespace: dap-course-g01
spec:
  ingressClassName: nginx
  rules:
    - host: gw-g01.dap-course.local     # 本组域名
      http:
        paths:
          - path: /
            pathType: Prefix
            backend: { service: { name: dap-gateway, port: { number: 8000 } } }
```

Secret 只提交占位文件 `dap-gateway-secret.yaml.example`（真实 Secret 由企业导师现场发放/CI 注入，不入 Git）。

#### 子步骤 2：部署与四跳验证（25′）

```bash
kubectl -n dap-course-g01 apply -f dap-gateway-lab.yaml
kubectl -n dap-course-g01 get pods -o wide                 # 2/2 Running
kubectl -n dap-course-g01 describe pod -l app=dap-gateway  # 看 Events 与探针配置
kubectl -n dap-course-g01 get endpoints dap-gateway        # 第3跳：Endpoints 已含 2 个 PodIP
curl -s -H "Host: gw-g01.dap-course.local" http://10.167.2.175/healthz   # 200
curl -s -H "Host: gw-g01.dap-course.local" http://10.167.2.175/api/ping  # {"pong":true}
```

四跳取证：Ingress 规则（host/path）→Service selector 与 port→Endpoints PodIP 列表→Pod 内进程，把每跳证据截图贴入流量追踪图。

任一验收不过时的排障速查（按序执行，禁止无脑删了重建）：

```bash
kubectl -n dap-course-g01 describe pod -l app=dap-gateway   # 先看 Events：镜像拉取？探针失败？挂载失败？
kubectl -n dap-course-g01 logs deploy/dap-gateway --tail=50  # 再看应用日志：配置缺失？依赖连不上？
kubectl -n dap-course-g01 get ingress dap-gateway -o yaml    # 再核路由：host/path/backend 是否匹配
```

#### 子步骤 3：三组故障实验（25′）

| 实验 | 操作 | 预期现象（须截图 events/endpoints 佐证） |
|---|---|---|
| 自愈 | `kubectl -n dap-course-g01 delete pod -l app=dap-gateway` （删 1 个） | ReplicaSet 秒级重建新 Pod；重建期间 Endpoints 只剩 1 个 IP，服务经另一副本不中断 |
| 依赖故障 | 停掉课程 Redis（`kubectl -n dap-course-g01 scale deploy/dap-lab-redis --replicas=0`） | /readyz 变 503→Pod 从 Endpoints 摘除→外部拿到的是 503 降级而非 502 连接错误；/healthz 仍 200；Pod 不重启 |
| 反例：liveness 误查依赖 | 临时把 livenessProbe 也指向 /readyz 后 apply | Redis 停止期间 kubelet 反复重启 Pod→CrashLoopBackOff——用事实记住"liveness 只查进程" |

实验后恢复 Redis 副本，确认 Pod 自动回到 Endpoints（依赖自愈闭环）。

#### 子步骤 4：滚动更新与回滚（20′）

```bash
# 循环探测放后台：watch curl -s -H "Host: gw-g01.dap-course.local" http://10.167.2.175/api/ping
kubectl -n dap-course-g01 set image deploy/dap-gateway gateway=registry.local/dap/gateway:course-v1.1
kubectl -n dap-course-g01 rollout status deploy/dap-gateway     # 逐个替换
kubectl -n dap-course-g01 rollout history deploy/dap-gateway
kubectl -n dap-course-g01 rollout undo deploy/dap-gateway       # 回滚演练
```

记录：滚动期间循环 curl 的成功率（应为 100% 或仅个别超时）、Surge/Unavailable 行为；对照事故通报说明"为什么现在的流程不会再 502"。

| 讲什么 | "就绪探针为什么不能只查进程存活"：用本组实验讲清三个事实——①进程活着≠能干活（Redis 断了 /healthz 仍是 200）；②readiness 摘流量、liveness 才重启，分工不能互换；③把 liveness 指向 /readyz 会让依赖抖动变成重启风暴（CrashLoopBackOff 实录）。允许画" kubelet - Pod - Endpoints - 流量"四格图 |
| 自评三问 | ① 我能只用"门口挂牌"这类生活比喻讲清两种探针分工吗？② 我卡壳在哪——Endpoints 摘除机制还是优雅关停时序？③ 卡壳处回炉：本讲故障实验记录单＋《平台部署公约》探针章节；仍不通则下次课企业站请教导师实操演示 |

**讲述提纲提示**：先用"进程活着≠能干活"一句话立论→再讲本组 Redis 停止实验的两个截图（readyz 503 摘流量／healthz 200 不重启）→ 最后讲反例 CrashLoop 的因果链收尾。
