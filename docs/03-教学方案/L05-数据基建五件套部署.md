## 〇、本讲术语小白卡（先看懂再开工）

| 术语 | 人话解释 | 生活化类比 |
|---|---|---|
| 中间件 | 不直接面对用户、专给程序打下手的后台服务 | 餐厅后厨：客人看不见，没它出不了菜 |
| HTAP | 一份数据既能记账（交易）又能做报表（分析） | 收银机连着报表系统，账本只有一本 |
| 消息队列 | 任务先排队再做，高峰期不压垮处理方 | 传菜口：高峰期先排队，做一份取一份 |
| 向量数据库 | 按"长得像不像"找内容的知识索引柜（L08 细讲） | 按照片找相似包裹的智能仓库 |
| GitOps | 仓库清单是唯一真相：想改什么，先改本子再动手 | 先改图纸再施工，禁止直接砸墙 |
| 漂移 drift | 线上实际状态和清单写的不一样了 | 图纸画 2 扇窗，现场只装了 1 扇 |
| overlay | 同一份底稿＋不同场景的批注补丁 | 同一份试卷模板，不同班级加不同姓名条 |

## 四、教学重点与难点

**教学重点**
1. 五件套分工与"为什么选它"：TiDB HTAP 一份数据同时扛交易与分析、CRDB 强一致 + 读写分离拓扑、Milvus 高维向量近邻检索、Pulsar 持久化队列 + 死信重投、Redis 微秒级热路径缓存与限流。
2. GitOps 部署闭环：`读清单 → diff 预览 → apply 应用 → 等就绪 → 逐件验证 → diff 归零`。

```flow
读部署清单 → ① diff 预览 → ② apply 应用 → ③ 等 Pod 就绪 → ④ 逐件验证 → ⑤ diff 归零 → 交付验收单
```

**教学难点**
1. 五件套功能边界易混淆（学生常问："Milvus 和 Redis 都是'缓存'？"、"Pulsar 和 Redis 的 List 都是'队列'？"）。
   **突破策略（三步台阶）**：
   - 台阶1·类比直觉：五件套＝一个物流园——TiDB＝总仓库（又能盘点又能开单）、CRDB＝调度档案室（前台登记窗口/后台查询窗口分开设＝读写分离）、Milvus＝按照片找相似包裹的仓库、Pulsar＝传送带＋异常件暂存架（DLQ）、Redis＝门口便利贴墙（最常问的答案贴着，不用进仓库）。
   - 台阶2·看演示：教师用"去掉它会坏什么"反事实提问现场演示一次（拔掉 Pulsar，看长任务堆积）。
   - 台阶3·动手复现：每组现场回答两个反事实问题后再填对比矩阵（一致性 / 持久化 / 查询模型 / 延迟量级四列）。
2. 漂移（drift）概念的抽象性：live 集群状态与 git 声明的差异学生难以感知。
   **突破策略（三步台阶）**：
   - 台阶1·类比直觉：图纸写 2 扇窗、现场只装 1 扇——验收员（diff）一眼就能查出来；
   - 台阶2·看演示：教师先演示一次 `kubectl diff` 输出的红绿差异行怎么读；
   - 台阶3·动手复现：实施第 3 子步骤**亲手制造一次漂移**（手动 scale），亲眼看到 diff 输出差异并修复归零，把抽象概念变成一次可复现事件。
3. GitOps/Kustomize/overlay 三个前置概念零基础。
   **突破策略（三步台阶）**：台阶1：GitOps＝"仓库是唯一真相"、overlay＝"同一底稿＋班级批注"（见术语卡）；台阶2：教师投屏 dap-v2 仓库 `deploy/k8s/` 真实扁平 8 个 yaml 结构，指认哪个是 Redis、哪个是 PDB；台阶3：学生打开课程分支 `labs/L05/` 清单目录，找到自己 ns 要 apply 的文件并说出它声明了什么。

## 六、教学过程设计（六步法：资讯 30′/计划 30′/决策 20′/实施 90′/检查 40′/评价+学生讲堂 30′）

### 6.1 资讯（30′）

**【教师活动】**
1. 发放委托单 DAP-DEPLOY-05，用 5 分钟讲清交付物：五件套全绿 + 漂移归零 + 验收单。
2. **5′"两分钟看懂拓扑图"**：板书 DAP-v2 数据面拓扑，逐条连线讲一遍再发对照矩阵（先给图，再给表）：`dap-gateway(FastAPI+Strawberry GraphQL)` → 平台库 CRDB（写 `cockroachdb-a:26257` / 读 `cockroachdb-b:26267`）｜洞察 Agent → 目标数仓 TiDB（NodePort `30210`，专库账号 `dap_app`）+ Milvus `:19530`｜任务面 Pulsar `:6650`（`persistent://dap/prod/jobs`，6 分区）｜热路径 Redis。同步讲清 ADR-001 的关键决策：**TiDB/CRDB/Milvus/Pulsar 四件复用集群 infra 共享实例，课程 ns 内只部署 dap-redis 等课程裁剪件**——"四件是租来的房子，一件是自己买的家具"。
3. **物流园类比先行**（先给整体图景再进细节）：五件套＝一个物流园——TiDB＝总仓库（又能盘点又能开单＝HTAP）、CRDB＝调度档案室（前台登记窗口和后台查询窗口分开设＝读写分离）、Milvus＝按照片找相似包裹的仓库、Pulsar＝传送带＋异常件暂存架（DLQ）、Redis＝门口便利贴墙（最常问的答案贴着，不用进仓库）。**向量概念今天不学**：Milvus 的"向量"与 `dap_semantic_cache` 的 cosine≥0.92 在 L08 细讲，今天只需知道 Milvus 是"知识库的索引柜"。
4. 带领填写五件套选型对照矩阵（重点：每行"为什么选它"必须能说出替代品为什么不行）：

| 组件 | 版本:端口 | 解决的核心问题 | 为什么选它（对比项） | 去掉它会坏什么 |
|---|---|---|---|---|
| TiDB | v8.5.8 :4000（集群 NodePort 30210 对外） | 数仓 OLAP 分析 + HTAP | TiKV 行存 + TiFlash 列存同一份数据，免"再导一份到 ClickHouse"；国产自主可控（课程思政点） | NL2SQL 沙箱执行无处跑，105.9 万订单分析退回手工导表 |
| CRDB | 写 26257 / 读 26267 | 平台元数据、用户、审计的强一致存储 | PostgreSQL 协议兼容（SQL 零改造）、raft 强一致、天然支持双集群读写分离拓扑 | 网关无平台库；读写分离（L06）失去载体 |
| Milvus | v2.6.6 :19530 | 向量近邻检索 | 十亿级向量 ANN 索引 + 标量过滤；`dap_knowledge`（知识）与 `dap_semantic_cache`（语义缓存）两个 collection（cosine≥0.92 的含义 L08 细讲） | RAG 检索（L08）与语义缓存全部失效，问句必须每次裸调 LLM |
| Pulsar | 4.0.5 :6650 | 异步任务持久化队列 | BookKeeper 分层持久化、消息可重放、6 分区并行消费；应用侧 DLQ 承接 redelivery≥3 的毒丸消息（DLP 铁律） | 长任务丢失、失败任务无限重试堵死队列 |
| Redis | 7.x | 热点缓存 + 分布式限流 | 微秒级；令牌桶 Lua 脚本原子限流 | 每问句全量打 CRDB/TiDB，高峰限流失效雪崩 |

4. 穿插两个真实"依赖漂移"教训（10′）：① `numpy 2.x` 在 X86_V2 CPU 上直接 `Illegal instruction`——所以 `requirements.txt` 钉死 `numpy>=1.26,<2.0`；② `pymilvus` 插入主键必须 int64，字符串 id 报 schema 不匹配。结论：**部署清单 = 镜像版本 + 依赖版本双钉**。

**【学生活动】** 接收委托单；跟随拓扑图在自己纸上复画数据流；结对完成对照矩阵"去掉它会坏什么"两问；记录两个依赖坑到任务单"风险栏"。

**【教学方法】** 客户委托单导入 + 讲授 + 反事实提问（对比分析）。

**【设计意图】** 用"委托单 + 反事实"把记忆层信息（版本/端口/角色）转成理解层判断（选型权衡）；依赖坑案例为实施第 4 子步骤的版本核验埋伏笔。

### 6.2 计划（30′）

**【教师活动】** 投屏 dap-v2 仓库根 `Makefile` 关键目标与 `deploy/k8s/` 真实结构，示范如何读部署计划：

```
dap-v2/
├── Makefile               # 仓库根（目标：deploy / diff / seed / test / smoke / e2e / load-test）
├── deploy/k8s/            # 扁平 8 个 yaml（GitOps 单一事实源）
│   ├── 00-namespace-config.yaml   01-redis.yaml      02-tools.yaml
│   ├── 03-worker.yaml     04-gateway.yaml    05-init-jobs.yaml
│   └── 06-pdb.yaml        07-backup.yaml
├── seed/seed_warehouse.py # 灌数脚本（make seed 调用）
└── labs/L05/              # 课程裁剪清单目录（教师发放到课程分支，学生 ns 可部署件）
```

> 注意两个真实约束：① 仓库 `make diff` 目标内部是 `scp yaml 到 master 再 kubectl diff`，需要 root 权限——学生用课程 ns 原生命令 `kubectl -n $NS diff -f labs/L05/`（只读权限即可，DGO 思想一致）；② `make deploy` 同理是生产发布通道，课程不用。

```bash
# 课程 ns 的 GitOps 闭环（labs/L05/ 为教师裁剪的课程清单）
kubectl -n dap-course-g1 diff -f labs/L05/    # 漂移预览：不改动任何资源
kubectl -n dap-course-g1 apply -f labs/L05/   # 声明式应用（git 为唯一事实源）
kubectl -n dap-course-g1 get pods -o wide     # 看状态
```

**【学生活动】** 结对制定《部署计划表》：① 验证顺序及理由（提示：先课程 ns 内部署件，再逐件连通验证 infra 共享件）；② 每件套的验证命令清单（每人至少写 2 条）；③ 时间盒分配（90′ 实施）；④ 风险与回滚方式（`kubectl delete -f labs/L05/` / 重新 apply 重推）。

**【教学方法】** 引导文法（Leittext）：计划表只给栏目标题，内容由学生从 Makefile 与 yaml 中自行挖掘。

**【设计意图】** 计划环节强迫学生先读声明文件再动手，避免"上来就 apply"的冲动；验证命令清单直接供 6.4 使用，形成闭环。

### 6.3 决策（20′）

**【教师活动】** 逐组快速过计划表，只把关两件事：① 是否"**先 diff 后 apply**"（diff 非零 = 有漂移或首次部署，必须能解释每一行差异）；② 验证顺序是否考虑依赖（先课程 ns 内 dap-redis 就绪，再从课程 ns 向 infra 五件逐一连通验证）。宣布纪律：**禁止 `kubectl edit/scale` 直接改 live**（DGO 铁律），一切变更改清单文件后经 `kubectl apply -f` 重推。

**【学生活动】** 汇报计划要点（每组 90 秒）；根据教师反馈修订计划表并签字确认。

**【教学方法】** 决策会（小组汇报 + 教师否决权）。

**【设计意图】** 双元制"决策"步骤训练工程判断：顺序与纪律比速度重要；把 GitOps 铁律变成课堂硬约束。
