## 三、学习目标

## 四、教学重点与难点

**教学重点**
1. 五件套分工与"为什么选它"：TiDB HTAP 一份数据同时扛交易与分析、CRDB 强一致 + 读写分离拓扑、Milvus 高维向量近邻检索、Pulsar 持久化队列 + 死信重投、Redis 微秒级热路径缓存与限流。
2. GitOps 部署闭环：`git 仓库 → make diff（dry-run 漂移预览）→ make apply → make diff 复核归零`。

**教学难点**
1. 五件套功能边界易混淆（学生常问："Milvus 和 Redis 都是'缓存'？"、"Pulsar 和 Redis 的 List 都是'队列'？"）。
   **突破策略**：用"去掉它会坏什么"反事实提问 + 对比矩阵（一致性 / 持久化 / 查询模型 / 延迟量级四列），让每组现场回答两个反事实问题后再填表。
2. 漂移（drift）概念的抽象性：live 集群状态与 git 声明的差异学生难以感知。
   **突破策略**：实施第 3 子步骤中**亲手制造一次漂移**（手动 scale），亲眼看到 `make diff` 输出差异并修复归零，把抽象概念变成一次可复现事件。

### 6.1 资讯（30′）

**【教师活动】**
1. 发放委托单 DAP-DEPLOY-05，用 5 分钟讲清交付物：五件套全绿 + 漂移归零 + 验收单。
2. 板书 DAP-v2 数据面拓扑：`dap-gateway(FastAPI+Strawberry GraphQL)` → 平台库 CRDB（写 `cockroachdb-a:26257` / 读 `cockroachdb-b:26267`）｜洞察 Agent → 目标数仓 TiDB `:4000`（专库账号 `dap_app`）+ Milvus `:19530`｜任务面 Pulsar `:6650`（`persistent://dap/prod/jobs`，6 分区）｜热路径 Redis。
3. 带领填写五件套选型对照矩阵（重点：每行"为什么选它"必须能说出替代品为什么不行）：

| 组件 | 版本:端口 | 解决的核心问题 | 为什么选它（对比项） | 去掉它会坏什么 |
|---|---|---|---|---|
| TiDB | v8.5.8 :4000 | 数仓 OLAP 分析 + HTAP | TiKV 行存 + TiFlash 列存同一份数据，免"再导一份到 ClickHouse"；国产自主可控（课程思政点） | NL2SQL 沙箱执行无处跑，105.9 万订单分析退回手工导表 |
| CRDB | 写 26257 / 读 26267 | 平台元数据、用户、审计的强一致存储 | PostgreSQL 协议兼容（SQL 零改造）、raft 强一致、天然支持双集群读写分离拓扑 | 网关无平台库；读写分离（L06）失去载体 |
| Milvus | v2.6.6 :19530 | 向量近邻检索 | 十亿级向量 ANN 索引 + 标量过滤；`dap_knowledge`（知识）与 `dap_semantic_cache`（cosine≥0.92 语义缓存）两个 collection | RAG 检索（L08）与语义缓存全部失效，问句必须每次裸调 LLM |
| Pulsar | 4.0.5 :6650 | 异步任务持久化队列 | BookKeeper 分层持久化、消息可重放、6 分区并行消费；应用侧 DLQ 承接 redelivery≥3 的毒丸消息（DLP 铁律） | 长任务丢失、失败任务无限重试堵死队列 |
| Redis | 7.x | 热点缓存 + 分布式限流 | 微秒级；令牌桶 Lua 脚本原子限流 | 每问句全量打 CRDB/TiDB，高峰限流失效雪崩 |

4. 穿插两个真实"依赖漂移"教训（10′）：① `numpy 2.x` 在 X86_V2 CPU 上直接 `Illegal instruction`——所以 `requirements.txt` 钉死 `numpy>=1.26,<2.0`；② `pymilvus` 插入主键必须 int64，字符串 id 报 schema 不匹配。结论：**部署清单 = 镜像版本 + 依赖版本双钉**。

**【学生活动】** 接收委托单；跟随拓扑图在自己纸上复画数据流；结对完成对照矩阵"去掉它会坏什么"两问；记录两个依赖坑到任务单"风险栏"。

**【教学方法】** 客户委托单导入 + 讲授 + 反事实提问（对比分析）。

**【设计意图】** 用"委托单 + 反事实"把记忆层信息（版本/端口/角色）转成理解层判断（选型权衡）；依赖坑案例为实施第 4 子步骤的版本核验埋伏笔。

### 6.2 计划（30′）

**【教师活动】** 投屏 `deploy/` 目录结构与 `Makefile` 关键目标，示范如何读部署计划：

```
deploy/
├── Makefile                 # diff / apply / ps / destroy 目标
└── k8s/
    ├── base/                # 五件套 + dap-gateway 的 Kustomize base
    │   ├── tidb-cluster.yaml      cockroachdb-a.yaml  cockroachdb-b.yaml
    │   ├── milvus.yaml            pulsar.yaml          redis.yaml
    └── overlays/course/      # 课程 ns 补丁：资源配额收敛、NodePort、课程镜像 tag
```

```makefile
# deploy/Makefile（节选）
NS ?= dap-course-g1
diff:   ## 漂移预览：git 声明 vs 集群 live（不改动任何资源）
	kubectl diff -k k8s/overlays/course -n $(NS)
apply:  ## 声明式应用（git 为唯一事实源）
	kubectl apply -k k8s/overlays/course -n $(NS)
ps:
	kubectl -n $(NS) get pods -o wide
```

**【学生活动】** 结对制定《部署计划表》：① 部署顺序及理由（提示：存储类先行，网关最后）；② 每件套的验证命令清单（每人至少写 2 条）；③ 时间盒分配（90′ 实施）；④ 风险与回滚方式（`kubectl delete -k` / `make apply` 重推）。

**【教学方法】** 引导文法（Leittext）：计划表只给栏目标题，内容由学生从 Makefile 与 yaml 中自行挖掘。

**【设计意图】** 计划环节强迫学生先读声明文件再动手，避免"上来就 apply"的冲动；验证命令清单直接供 6.4 使用，形成闭环。

#### 子步骤 3（20′）：漂移制造与修复实验（本讲核心体验）

```bash

kubectl -n $NS scale deploy/redis-master --replicas=1

# ④ 复核归零：
make diff NS=$NS && echo "CLEAN"
```

### 任务卡 PR-05：TiDB 灌数验证（105.9 万行）

| 项目 | 内容 |
|---|---|
| 任务目标 | 向 TiDB 目标数仓灌入零售样例数据，验证 105.9 万订单全量可查、抽样业务问题可答 |
| 前置条件 | L05 校内部署验收 8 项中 ≥6 项通过；`dap_app` 账号可连 `10.167.2.175:4000` |
| 结对方式 | 2 人结对，Driver/Navigator 30′ 轮换；在企业导师见证下操作课程分支 |

**步骤：**

```bash
# 1. 灌数（脚本内部按 ODS→DWD/DIM→DWS→ADS 顺序执行，幂等可重跑）
mysql -h 10.167.2.175 -P 4000 -u root -p < scripts/seed/create_retail_schema.sql
zcat data/retail_warehouse.sql.gz | \
  mysql -h 10.167.2.175 -P 4000 -u root -p --local-infile=1 retail_dw

# 2. 行数铁证（预期 1,059,3xx，以实际灌数为准，截图入 PR）
mysql -h 10.167.2.175 -P 4000 -u dap_app -p -e \
 "SELECT COUNT(*) FROM retail_dw.ods_orders;"        # ≈ 1,059,000+
mysql -h ... -e "SELECT COUNT(*) FROM retail_dw.dwd_order_items;"
mysql -h ... -e "SELECT COUNT(*) FROM retail_dw.dim_products;"

# 3. 三条业务抽验 SQL（必须用 dap_app 只读账号执行）
# Q1 品类销售 Top3：
SELECT p.category, SUM(i.pay_amount) amt FROM dwd_order_items i
  JOIN dim_products p ON i.product_id=p.product_id
  GROUP BY p.category ORDER BY amt DESC LIMIT 3;
```
