# 学习情境 L11：质量规则引擎与主动巡检（6 学时）

> 载体：DAP-v2 质量 Agent——五类确定性规则（null_rate / uniqueness / range / row_variance / freshness）以 SQL 探针实现，8 条种子规则（qr-gmv-null 等）日巡检；扫描→quality_results 落库→告警链路。

## 二、任务描述

> 【委托单 #R-2411】委托方：数据治理委员会。dws_gmv_daily 连续两天 GMV 空值率超 8%，下游报表与看板全部失真，直到业务投诉才发现。请把"空值率、唯一性、值域、行数波动、新鲜度"五类检查变成每天自动执行的探针，结果落库、失败即告警；不许再靠人肉盯表。——DAP-v2 质量巡检上线任务单

## 三、学习目标

1. 【记忆/理解】说出五类质量规则（null_rate / uniqueness / range / row_variance / freshness）各自守护的缺陷形态、典型阈值与适用表型（事实表/维表/汇总表）。
2. 【应用】在数仓终端手工执行一条规则的探针 SQL，正确解读返回指标值与阈值的比较方向（大于失败/小于失败）。
3. 【分析】复现并修复 CRDB JSONB 字符串类型坑：驱动把 `quality_rules.params` 还原成 str 导致 `row["params"]["threshold"]` 抛 TypeError，解释 `_params_of` 的双态兼容写法，并归纳"驱动类型系统 ≠ 数据库类型系统"。
4. 【分析】追踪"扫描调度 → 探针执行 → quality_results 落库 → 告警"全链路，指出一条失败记录上每个证据字段（metric_value / threshold / checked_at / partition）的含义。
5. 【评价】论证"规则为主、LLM 为辅"的职责边界：判定必须确定性、可回归、可审计；归因与规则推荐才交给 LLM（为 L12 埋伏笔）。

## 四、教学重点与难点

**教学重点**

1. 五类规则的 SQL 探针实现（`probes.py` 的 PROBES 字典）：模板化、参数化、只读、带分区过滤。
2. 巡检链路落库与告警：quality_results 的证据字段设计与失败判定方向。

**教学难点（附突破策略）**

1. **CRDB JSONB 字符串坑**：`SELECT params` 拿到的是 `str`，按 dict 取键直接 TypeError，且报错位置离根因很远（在探针格式化 SQL 时才爆）。
   - 突破策略：先踩后修——课程分支 `edu-bug/params` 保留了原始 bug，学生先跑 pytest 看到 `TypeError: string indices must be integers`，回溯到 `type(row["params"])` 是 str；再读 `_params_of` 双态兼容；最后归纳同类坑清单（TiDB DECIMAL→str、MySQL JSON→str），形成"读驱动文档先于写代码"的习惯。
2. **规则与 LLM 的职责边界**：学生直觉认为"LLM 什么都能判"。
   - 突破策略：反例辩论——"让 LLM 判空值率会怎样"四宗罪（不可回归：同输入不同输出；不可解释：为何 0.08>0.05 要靠嘴说；成本：每天 8 规则×N 分区白烧 token；漂移：prompt 一改结论变）；再给三判据（确定性/可重放/可审计）让学生自己裁决 6 个场景归规则还是归 LLM。

```python
# dap-v2/services/quality-agent/probes.py（节选）
PROBES = {
    "null_rate":    "SELECT AVG(CASE WHEN {col} IS NULL THEN 1.0 ELSE 0 END) AS v "
                    "FROM {tbl} WHERE dt = '{ds}'",
    "uniqueness":   "SELECT 1.0 - COUNT(DISTINCT {uk}) * 1.0 / NULLIF(COUNT(*), 0) AS v "
                    "FROM {tbl} WHERE dt = '{ds}'",          # v = 重复率，0 为最好
    "range":        "SELECT AVG(CASE WHEN {col} BETWEEN {lo} AND {hi} THEN 0.0 ELSE 1 END) AS v "
                    "FROM {tbl} WHERE dt = '{ds}'",          # v = 越界率
    "row_variance": "SELECT ABS(cnt - {expect}) * 1.0 / {expect} AS v "
                    "FROM (SELECT COUNT(*) AS cnt FROM {tbl} WHERE dt = '{ds}') t",
    "freshness":    "SELECT EXTRACT(EPOCH FROM (now() - MAX({ts_col}))) / 3600.0 AS v "
                    "FROM {tbl}",
}
# 判定统一：direction='lt' 时 v < threshold 为 FAIL（如 null_rate 0.08 < 0.05? 否→FAIL）
```

#### 4.2 踩坑复现与修复：CRDB JSONB 字符串坑（20′）

```bash
# ① 先跑"想当然"版本（bug 分支保留了原始错误）
git switch edu-bug/params
pytest tests/quality/test_probes.py -x
# TypeError: string indices must be integers
#   —— 报错抛在探针 SQL 格式化处，离根因（params 是 str）隔了两层调用！

# ② 回到 CRDB 看真实类型
git switch edu/2026-spring
make crdb-sql
> SELECT params FROM quality_rules WHERE rule_id = 'qr-gmv-null';
-- {"col": "gmv", "tbl": "dws_gmv_daily"}     ← 看起来像 dict
> SHOW COLUMNS FROM quality_rules;            ← params 是 JSONB
-- 但驱动（psycopg2 族）把 JSONB 还原成了 str！
```

修复对照（`db.py` 的双态兼容）：

```python
def _params_of(row) -> dict:
    p = row.get("params") or {}
    if isinstance(p, str):        # CRDB/psycopg2 驱动把 JSONB 还原成 str
        p = json.loads(p)
    return p
```

```bash
pytest tests/quality/ -q    # 回归全绿
```

归纳卡（写入任务单）：驱动类型系统 ≠ 数据库类型系统；同类坑还有 TiDB DECIMAL→`Decimal("1.20")`、部分驱动 JSON→str；守则是"跨库边界取值先 `type()` 一下再取键"。

#### 4.4 边界辩论：规则为主、LLM 为辅（20′）

辩论卡 A（反方必须先说赢）："空值率判定交给 LLM 会怎样？"——四宗罪：不可回归（同输入不同输出）、不可解释（0.08>0.05 还要靠嘴说）、成本（8 规则×30 分区×每天＝白烧 token）、漂移（prompt 改版结论变）。

裁决卡 B：用三判据（**确定性 / 可重放 / 可审计**）逐个裁决 6 场景归谁——
① 判 gmv 是否为空 → 规则；② 判断"为什么突然变空" → LLM（L12 归因）；
③ 判行数是否暴跌 50% → 规则；④ 起草一条新规则的建议 → LLM（人审后入库）；
⑤ 判敏感列是否要脱敏 → 规则＋人审；⑥ 写修复 SQL 草稿 → LLM（仅草稿，人批准）。

产出：每组为售后域起草 2 条新规则（类型/目标表/列/阈值/阈值依据/探针 SQL 预览），企业站真正入库验证。

## 九、课后费曼任务

- **讲给谁**：同班同学（懂 SQL 但没上过本讲）或实习单位的同事。
- **讲什么**："规则为主、LLM 为辅"的边界——用三判据（确定性/可重放/可审计）讲清为什么空值率这种事绝不能交给 LLM 判，而"为什么变空"却恰恰适合 LLM。
- **自评三问**：①我能不看卡片说出三判据并各举一例吗？②对方能复述"判定和归因是两件事"吗？③我举的 LLM 判定翻车场景，对方能听出是四宗罪里的哪一条吗？——任一问答"否"，重讲并录音自查。
