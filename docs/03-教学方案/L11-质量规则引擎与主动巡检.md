## 四、教学重点与难点

**教学重点**

1. 五类规则的 SQL 探针实现（`services/tools/main.py` 的 `_run_rule` probes 字典）：模板化、参数化、只读。
2. 巡检链路落库与失败处置：quality_results 的证据字段设计（status / metric_value / detail / suggestion）与按类型的判定方向。

**质量巡检守护链（课堂板书/PPT 用）**

```flow
定时触发 → ①取启用规则 → ②拼探针SQL → ③数仓执行 → ④比对阈值方向 → ⑤结果落库 → ⑥失败项附建议
```

**教学难点（附突破策略）**

1. **CRDB JSONB 字符串坑**：`SELECT params` 拿到的是 `str`，按 dict 取键直接 TypeError，且报错位置离根因很远（在探针格式化 SQL 时才爆）。
   - 三步台阶：台阶1（生活类比建立直觉）——数据库里的 params 是"装在塑封袋里的便利贴"（JSONB），有的司机（驱动）送货时会帮你拆袋（自动转 dict），有的不会（还原成 str）——不拆袋就伸手去翻便利贴，当然出错；台阶2（看一次真实演示）——教师先跑踩坑用例投屏 `TypeError: string indices must be integers`，再在 CRDB 里 `type()` 演示 params 真实类型；台阶3（学生动手复现）——课程分支 `edu-bug/params` 保留了原始 bug，学生先复现看到 TypeError，回溯到 `type(row["params"])` 是 str；再读 `_params_of` 双态兼容；最后归纳同类坑清单（TiDB DECIMAL→str、MySQL JSON→str），形成"读驱动文档先于写代码"的习惯。
2. **规则与 LLM 的职责边界**：学生直觉认为"LLM 什么都能判"。
   - 三步台阶：台阶1（生活类比建立直觉）——判定规则＝体温计：高烧自动叫人，但**只在开始发烧时叫**，不每分钟喊一遍（否则人人告警疲劳）；LLM＝会分析病情的医生：适合回答"为什么发烧"，不适合当体温计；台阶2（看一次真实演示）——教师让 LLM 现场判同一个空值率两次，两次措辞/结论粒度不同，学生亲眼看到"不可回归"；台阶3（学生动手复现）——反例辩论"让 LLM 判空值率会怎样"四宗罪（不可回归：同输入不同输出；不可解释：为何 0.08>0.05 要靠嘴说；成本：每天 8 规则×N 分区白烧 token；漂移：prompt 一改结论变）；再给三判据（确定性/可重放/可审计）让学生自己裁决 6 个场景归规则还是归 LLM。

```python
# dap-v2/services/tools/main.py（_run_rule 节选，真实代码）
probes = {
    "null_rate":    "SELECT COUNT(*) AS total, SUM(CASE WHEN {col} IS NULL THEN 1 ELSE 0 END) "
                    "AS bad FROM {tbl}",
    "uniqueness":   "SELECT COUNT(*) AS total, COUNT(*) - COUNT(DISTINCT {col}) AS bad FROM {tbl}",
    "range":        "SELECT COUNT(*) AS total, SUM(CASE WHEN {col} < {min} OR {col} > {max} "
                    "THEN 1 ELSE 0 END) AS bad FROM {tbl}",
    "row_variance": "SELECT COUNT(*) AS total, COUNT(*) AS bad FROM {tbl}",
    "freshness":    "SELECT TIMESTAMPDIFF(HOUR, MAX({col}), NOW()) AS age_hours, "
                    "COUNT(*) AS total FROM {tbl}",
}
# 判定方向按类型固定（代码写死，不是配置）：
#   null_rate：坏行占比 > params.max → FAIL；uniqueness：重复占比 > max_dup_ratio → FAIL
#   range：违规行数 ≠ 0 → FAIL；row_variance：行数/基线 < min_ratio → FAIL
#   freshness：最新数据距今 > max_hours → FAIL
```

修复对照（`services/tools/main.py` 的 `_params_of`，真实代码）：

```python
def _params_of(rule: dict[str, Any]) -> dict[str, Any]:
    """CRDB JSONB 以 str 返回（非 PG 自动解析），统一适配。"""
    p = rule.get("params")
    if isinstance(p, str):
        try:
            return json.loads(p or "{}")
        except json.JSONDecodeError:
            return {}
    return p or {}
```

```bash
pytest <教师下发的踩坑用例> -q    # 回归全绿
```

#### 4.4 边界辩论：规则为主、LLM 为辅（20′）

辩论卡 A（反方必须先说赢）："空值率判定交给 LLM 会怎样？"——四宗罪：不可回归（同输入不同输出）、不可解释（0.08>0.05 还要靠嘴说）、成本（8 规则×30 分区×每天＝白烧 token）、漂移（prompt 改版结论变）。

裁决卡 B：用三判据（**确定性 / 可重放 / 可审计**）逐个裁决 6 场景归谁——
① 判 gmv 是否为空 → 规则；② 判断"为什么突然变空" → LLM（L12 归因）；
③ 判行数是否暴跌 50% → 规则；④ 起草一条新规则的建议 → LLM（人审后入库）；
⑤ 判敏感列是否要脱敏 → 规则＋人审；⑥ 写修复 SQL 草稿 → LLM（仅草稿，人批准）。

产出：每组为售后域起草 2 条新规则（类型/目标表/列/阈值/阈值依据/探针 SQL 预览），企业站真正入库验证。

### 第 5 步：检查（40 分钟）

【教师活动】发布检查清单；重点抽查两组现场口头复述 _params_of 坑（不看笔记）。
【学生活动】自查＋互查：
1. 8 条种子规则的"人肉巡检"矩阵完整且判定正确；
2. 踩坑证据：TypeError 截图＋`type(params)` 验证＋修复 diff；
3. quality_results 8 行查询结果＋失败项 suggestion 证据；
4. 链路三问回答完整；
5. 裁决卡 6 场景结论与三判据自洽；
6. 售后域 2 条新规则草案含阈值依据；
7. 未验证/未完成清单如实标注。

【教学方法】核对表法＋口头快问快答。

【设计意图】口头复述逼出真实掌握度（防复制粘贴）；"阈值依据"检查项防止拍脑袋定阈值。

### 第 6 步：评价＋学生讲堂（30 分钟）

【教师活动】主持讲堂（抽 3 组各 4′）＋评分＋布置任务。
【学生活动】讲堂主题抽签二选一：①"我踩的那个 JSONB 坑：报错在三层之外"；②"如果让 LLM 当规则引擎：一场灾难的推演"。互评量表打分。
【教学方法】费曼法＋同伴互评。
【设计意图】讲坑比讲正确答案更能暴露与巩固理解；主题②直接为课后费曼任务打底。

## 九、课后费曼任务

- **讲给谁**：同班同学（懂 SQL 但没上过本讲）或实习单位的同事。
- **讲什么**："规则为主、LLM 为辅"的边界——用三判据（确定性/可重放/可审计）讲清为什么空值率这种事绝不能交给 LLM 判，而"为什么变空"却恰恰适合 LLM。
- **自评三问**：①我能不看卡片说出三判据并各举一例吗？②对方能复述"判定和归因是两件事"吗？③我举的 LLM 判定翻车场景，对方能听出是四宗罪里的哪一条吗？——任一问答"否"，重讲并录音自查。
