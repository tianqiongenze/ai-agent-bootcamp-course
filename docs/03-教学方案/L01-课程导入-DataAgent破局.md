# 学习情境 L01：当取数要排队两天——Data Agent 破局（6 学时）

## 一、学习情境基本信息

| 学习领域 | LF | 讲次 | 学时 | 布鲁姆主层级 | 双元场地 |
|---|---|---|---|---|---|
| LF1 数据中台认知与数仓架构规划 | LF1（第 1/3 讲） | L01 | 6（校内 4 ＋ 企业站 2） | 记忆 / 理解（记/解），应用渗透 | 校内理实一体教室 ＋ 企业实训站（dap-v2 两节点 K8S 集群） |

- **企业站 PR 任务**：环境 onboard——开通集群只读账号、克隆课程仓库并切到 `course/L01-baseline` 分支，提交首个 PR（内容：本组《虚拟数据部成立申请表.md》），走通 PR 规范。
- **课后费曼任务**：向一位非技术亲友解释"什么是 Data Agent、它凭什么把取数从 2 天缩到 5 分钟"，录 1 分钟音频提交。

## 二、任务描述

某零售集团数据部收到业务部门联名委托：门店运营要一份"上月 GMV 排名"竟排队 2 天，月度经营会经常拿到过期数据。CIO 要求数据部两周内交付三件事：量化诊断"取数为什么慢"、演示 DAP-v2 Data Agent 自助查数能力（含 420ms FAQ 直答）、给出数据部自身的能力转型清单。

## 三、学习目标

1. 【记忆】能默写传统取数链路 5 个环节（业务提单→开发排期→手写 SQL→测试校验→发布交付）及各环节典型耗时，随堂小测正确率 ≥80%。
2. 【记忆】能说出 DAP-v2 至少 5 项核心事实与指标：FAQ 直答 420ms（LLM 全链路 56s，约 130 倍）、held-out 24 题评测 91.7%（bootstrap CI 79.2–100）、k6 140RPS、105.9 万订单零售数仓、四层安全护栏、三级缓存。
3. 【理解】能用"取数排队 2 天"案例解释数据中台要解决的三个根本问题——口径不一致、链路太长、技能门槛高，并各举 1 个自己的例子。
4. 【理解】能按名称与顺序复述 NL2SQL 五步管线（Schema Linking→混合检索→LLM 生成 qwen2.5:14b→自校验→沙箱执行），并说出"为什么不能一步到位"的 2 条工程理由。
5. 【理解·素养】能陈述本组虚拟数据部三角色（数据工程/业务分析/质量治理）职责与轮值规则，并在课程公约（含"诚实报告缺陷"条款）上签名。

## 四、教学重点与难点

### 教学重点

1. 传统取数链路痛点与 Data Agent 破局点的一一对应：链路长→自然语言自助化；口径乱→知识引擎（CRDB 元数据＋Milvus 混合 RAG）；门槛高→NL 交互＋四层护栏兜底。
2. DAP-v2 端到端能力地图的整体印象：React 控制台→GraphQL/REST 网关（FastAPI+Strawberry）→LangGraph 风格编排→洞察/质量/根因/ETL 四 Agent→知识引擎→MCP 工具层（sql-executor）→TiDB 零售数仓（细讲留待 L03）。

### 教学难点（附突破策略）

1. **NL2SQL 五步管线为什么不"一步到位"**——学生易把 LLM 当魔法，认为一句提示词即可。
   突破策略：①"图书馆找书"类比：锁书架＝Schema Linking（105.9 万行、几十张表的搜索空间收敛）、翻索引卡＝混合检索、写读书笔记＝LLM 生成、自查一遍＝自校验（拦幻觉列名）、在阅览室试读＝沙箱执行（只读＋LIMIT）；②现场拆一条真实查询的五步管线日志，逐步看耗时与中间产物。
2. **从"学生心态"到"虚拟数据部员工心态"的角色转换**。
   突破策略：仪式感设计——颁发部门聘书、角色牌上墙、轮值表签字、课程公约集体签名；本讲起所有任务单以"部门"为单位提交并署角色名。

### 6.1 资讯（30′）

- 【教师活动】投屏 3 封脱敏的业务方催单邮件与 20 张取数工单，抛出主问题："一份 GMV 排名为什么要等 2 天？"；带领学生到 K8S 大屏前看 dap-v2 生产命名空间的真实 Pod 列表，说明"破局工具已投产"。
- 【学生活动】阅读工单，每人写 2 张痛点便签（现象＋猜测原因）贴上便签墙；按"等待久/口径吵/改不停"三类现场归堆。
- 【教学方法】工作坊研讨＋实物（工单）教学法。
- 【设计意图】用真实业务材料制造认知冲突，激活先修课经验，痛点由学生自己"发现"而非教师告知。

工单墙预埋三条线索（教师提前布置，供归纳时"恰好"被发现）：①同一需求三次返工的连锁工单；②跨部门口径冲突工单（GMV 含不含退款）；③积压超 5 天的"幽灵工单"（提单人已离职）。

**附：本讲术语速查表（随课程手册发放，资讯环节人手一份）**

| 术语 | 一句话解释（今天达到这个理解水平即可） |
|---|---|
| 数据中台 | 把"取数、算数、管口径"做成全公司共用的能力平台，而不是每个需求从零写 SQL |
| Data Agent | 能听懂自然语言、替业务去数仓查数并解释结果的智能体 |
| NL2SQL | 把"上月各门店 GMV 排名"这类自然语言翻译成 SQL 的技术 |
| FAQ 直答 | 高频标准问题走预先核准的答案库直接命中，420ms 级返回 |
| 混合检索 RAG | 向量相似＋关键词＋精确匹配多路召回知识，供生成时参考 |
| 四层护栏 | sqlglot 语法白名单／资源 LIMIT／租户表授权／审批，层层拦危险 SQL |
| held-out 评测 | 藏起来不给系统"复习"的 24 道题，专测真实水平（91.7%） |
| 语义缓存 | 问法不同但意思相同的问题直接复用答案（相似度阈值 0.92） |

### 6.2 计划（30′）

- 【教师活动】发放《痛点画像表》模板与统计口径（耗时＝交付时间−提单时间）；指导各组把 20 张工单按类型/耗时/返工次数分类统计，画出耗时分布条形图。
- 【学生活动】分工统计工单（业务分析角色主导），计算"平均排队时长、返工率、重复需求占比"三个数；数据工程角色列出每张工单涉及的表名（引出 ods_orders 等真实表）；质量治理角色记录口径冲突工单。
- 【教学方法】任务驱动＋小组协作。
- 【设计意图】用数据量化痛点，训练"用数据说话"的职业习惯（HSA 诚实文化第一课）。

《痛点画像表》统计栏模板：

| 统计项 | 口径定义 | 本组结果 |
|---|---|---|
| 平均排队时长 | 交付时间−提单时间（工作日口径） | |
| 返工率 | 有 ≥1 次口径修改的工单占比 | |

### 6.3 决策（20′）

- 【教师活动】提出决策任务："CIO 只给你 15 分钟演示，选哪 3 个场景最能证明 Data Agent 有效？"给出评审约束（必须覆盖：快、准、安全）。
- 【学生活动】各组讨论并锁定 3 个场景（预期方向：①FAQ 口径直答 420ms；②NL 查"上月各门店 GMV 排名前十"；③演示一条危险 SQL 被护栏拦截）；提交《演示验证清单》待教师确认可行性。
- 【教学方法】决策听证（教师逐组 3 分钟质询）。
- 【设计意图】在真实约束下做取舍，为实施环节的对照实验定靶。

候选演示场景池（教师供给，各组挑 3 并说明覆盖面）：

| 场景 | 证明点 | 风险提示 |
|---|---|---|
| FAQ 口径直答（420ms） | 快＋口径统一 | 需确认问句在直答库覆盖范围内 |
| NL 查门店 GMV 排名 | 准（直连数仓） | 首次生成走全链路，耗时波动大 |

| 同题两种问法同一结果 | 一致性 | 语义缓存未命中时对比不明显 |

### 6.4 实施（90′）

#### 子步骤 1：手工取数体验与痛点量化（25′）

用 TiDB 只读账号亲手跑一次"传统取数"，体验技能门槛：

```bash
mysql -h 10.167.2.176 -P 4000 -u course_ro -p -e "SELECT COUNT(*) AS cnt FROM ods_orders;"
# 预期 cnt ≈ 1,059,000（105.9 万订单，这就是业务方要的"数"的原料）
```

再尝试口算"上月各门店 GMV 排名前十"需要哪些表、哪些关联、哪些过滤——记录所需 SQL 技能点清单；对照工单统计出"排队 2 天"的时间去向（排期约占 60%、写 SQL 与测试约占 40%）。

技能点清单示例（预期学生列出）：多表 JOIN、退款冲抵逻辑、门店归属维表关联、测试数据过滤、分页与导出——这正是"业务方不会、数据部排队"的技能门槛实证。

#### 子步骤 2：NL 查数与 FAQ 直答对照实验（25′）

在 React 控制台完成两组对照，用秒表记录：

| 实验 | 操作 | 预期现象 |
|---|---|---|
| A. FAQ 直答 | 问"GMV 的统计口径是什么？" | 走直答链路，约 420ms 返回，界面标注直答来源 |
| B. 强制 LLM 全链路 | 同一问题关闭直答开关 | 走完整生成链路，约 56s——对比出约 130 倍差距 |
| C. NL 查数 | 问"2025 年 9 月各门店 GMV 排名前十" | 打开管线日志，依次看到 Schema Linking→混合检索→LLM 生成→自校验→沙箱执行五步及各自耗时 |

学生填写《演示验证记录表》：每步的输入/输出截图或摘要、总耗时、生成 SQL 是否可读。

演示 C 的生成 SQL 样例（预期系统产出，供对照判读——注意它命中的是预汇总层）：

```sql
-- 预期命中 dws_store_daily_sales（门店×日已汇总），而不是在 ods_orders 上现算
SELECT store_id, SUM(gmv_amt) AS gmv
FROM dws_store_daily_sales
WHERE stat_date BETWEEN '2025-09-01' AND '2025-09-30'
GROUP BY store_id
ORDER BY gmv DESC
LIMIT 10;
```

《演示验证记录表》五步耗时栏（对照管线日志逐行填写）：

| 步骤 | 观察要点 | 本组实测 |
|---|---|---|
| Schema Linking | 命中了哪些候选表/列 | |
| 混合检索 | 召回了哪些知识片段 | |
| LLM 生成 | SQL 是否可读、引用表是否正确 | |
| 自校验 | 是否发生回炉重生成（次数） | |
| 沙箱执行 | 行数、耗时、是否带 LIMIT | |

#### 子步骤 3：能力地图拼图（20′）

发放 8 张组件卡（React 控制台 / GraphQL 网关 FastAPI+Strawberry / LangGraph 风格编排 / 四 Agent / CRDB＋Milvus＋Nebula 知识引擎 / MCP sql-executor / TiDB 数仓 / Pulsar 异步）。各组按"一次提问的旅程"把卡片排成端到端链路并推举 1 人用 2 分钟讲解；教师对照官方架构图纠偏（本讲只求"顺序正确＋一句话职责"，细节留 L03）。

**过程性观察点**（教师随堂记录，不计分但作为"理解"层级佐证）：①便签墙是否出现"口径/排队/门槛"之外的自发洞察；②对照实验中是否主动追问"56s 花在哪一步"；③公约签名环节是否有学生质疑条款（视为高阶参与）。

**折算说明**：五维度得分相加即任务单百分制分；缺勤补做按 80% 计；互查放水（检查单全勾但教师抽查不过）该检查员所在维度减半——课程公约诚信条款适用。

## 九、课后费曼任务

| 项目 | 内容 |
