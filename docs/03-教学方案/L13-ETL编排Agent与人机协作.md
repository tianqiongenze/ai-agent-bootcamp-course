## 二、任务描述

> **客户委托单（客服部）**
> 客服部每日人工汇总昨日售后工单，常延误至中午且口径不一。现委托数据团队：每日 08:00 前将昨日售后工单按门店与品类汇总写入 DWS 层，并监控关键字段空值率。人手不足，请用 ETL 编排 Agent 生成任务草稿，并以审核工程师身份完成人机协作审批，使任务安全上线。

## 三、学习目标

1. 【理解】说出 ETL 编排 Agent 五步链路（业务需求解析→源表推荐·元数据检索→LLM 生成任务定义→草稿入库 pending_approval→工程师审核批准）各环节的输入、输出与失败分支。
2. 【应用】调用 Agent 将一条标准化业务需求转换为 etl_drafts 草稿，并逐字段解读任务定义 JSON（`target_table` / `sql_script` / `dag{cron, upstream_tasks}` / `quality_rules`）。
3. 【分析】对照源表元数据核查草稿 SQL 的表名、字段口径与聚合逻辑，定位至少 1 处需人工修正的问题（错表、错口径、错调度）。
4. 【评价】以 diff 修改量为量化证据，评判"标准化需求近直用、复杂需求好起点"的人机协作价值边界，形成书面审核意见（批准或驳回＋理由）。
5. 【创造】为本组售后域独立设计并提交一个可过审的 ETL 草稿 PR（含质量规则与 DAG 依赖说明）。

**目标—证据对照（评价依据）**

| 目标 | 达成证据（本讲产出） |
|---|---|
| 目标 1 | 四要素速查卡标注＋讲堂口述链路 |
| 目标 2 | curl 生成记录＋JSON 逐字段标注 |
| 目标 3 | 至少 1 处真实问题定位记录（指到字段） |
| 目标 4 | 双案例 diff 对照表＋书面审核意见 |
| 目标 5 | 企业站 PR（草稿 JSON＋拓扑说明） |

## 四、教学重点与难点

### 教学重点
1. ETL 任务定义 JSON 四要素（目标表/SQL/调度 DAG/质量规则）的结构语义，以及 Agent 如何由需求文本逐一生成。
2. 人审界面的状态流转与留痕要素（etl_drafts：`pending_approval → approved | rejected`，`reviewed_by / reviewed_at` 必填）。

### 教学难点
1. **评价"Agent 生成初稿"的真实价值边界**——学生易走向"Agent 万能"或"Agent 没用"两个极端。
   - 突破策略：双案例对照实验——同一 Agent 分别吃"标准化需求"（售后日报）与"复杂需求"（跨域回填），用 `git diff --stat` 的修改行数量化人工修正成本，让结论从数据中长出来而非教师灌输。
2. **DAG 依赖正确性判断**（`upstream_tasks` 指向谁、cron 与上游产出时间是否留了余量）。
   - 突破策略：给每组发"上游任务产出时刻表"，学生先画 DAG 草图再做拓扑检查，用"08:00 汇总但上游 08:05 才跑完"的反例做纠错练习。

## 六、教学过程设计

**六步法时间分配与关键产出**

| 步骤 | 时长 | 关键产出 |
|---|---|---|
| 资讯 | 30′ | 速查卡标注完成、疑问清单上墙 |
| 计划 | 30′ | 本组 requirement 初稿、自建审核清单 |
| 决策 | 20′ | 需求定稿、决策理由登记 |
| 实施 | 90′ | 草稿 JSON、审批闭环证据、双案例 diff 数据、课程分支草稿 |
| 检查 | 40′ | 交叉审核单（批准/驳回＋理由） |
| 评价＋学生讲堂 | 30′ | 互评分数、讲堂反馈条、"留哪层"必答句 |

### 第 1 步：资讯（30 分钟）

**【教师活动】** 投屏演示完整链路一次：输入需求文本→Agent 检索元数据推荐源表→生成任务定义 JSON→落 etl_drafts 待审；同步发放四要素速查卡，点明"生成的 INSERT 属非 SELECT 语句，按 L4 护栏必然转审批——Agent 天生无执行权"。
**【学生活动】** 精读 2 份真实草稿样本，用速查卡逐字段标注：目标表分层是否正确、SQL 用了哪些源表、cron 是几点、附带哪几条质量规则；列出"我看不懂的字段"贴到答疑板。
**【教学方法】** 演示法＋引导文法（速查卡即引导文）。
**【设计意图】** 先建立"产物长什么样"的整体图景，再进入操作；把 L14 的审批护栏提前挂钩，强化"建议权与执行权分离"的信任模型。

### 第 2 步：计划（30 分钟）

**【教师活动】** 布置双案例对照实验方案（案例 A 标准化／案例 B 复杂），给出量化口径（diff 行数＝人工修正成本）；组织各组起草自己的售后域需求一句话与审核清单。
**【学生活动】** 小组完成两件事：① 写出本组 requirement 初稿（含频率、粒度、目标层、监控项四要素）；② 共建审核清单，定稿后与教师基准版对照补漏。

审核清单六问（基准版，学生共建后对照）：

| 序号 | 检查项 | 判定依据 |
|---|---|---|
| 1 | 表名存在且分层正确 | 对照元数据表（meta）核验 |
| 2 | 字段口径与需求一致 | 需求关键词 ↔ SELECT 列一一对应 |
| 3 | 聚合粒度正确 | GROUP BY 维度＝需求的统计粒度 |
| 4 | 时间口径正确 | dt 过滤条件＝"昨日"，无跨日 |
| 5 | cron 晚于上游产出 | 查 DAG 产出时刻表留余量 |
| 6 | 质量规则覆盖监控项 | 需求点名的监控列有对应规则 |

**【教学方法】** 任务驱动＋小组共创。
**【设计意图】** 审核清单由学生自建而非发放，评价环节才有"自己的尺子"可用；需求四要素模板防止"一句话太糊"导致 Agent 生成跑偏。

### 第 3 步：决策（20 分钟）

**【教师活动】** 逐组快审 requirement：四要素是否齐、目标层是否明确（DWD/DWS）；用两个反例（"帮我做个售后报表"vs"每日 08:00 按门店品类汇总昨日工单量与完结率入 DWS，监控 order_id 空值率"）示范什么叫可执行的需求描述。
**【学生活动】** 按反馈定稿 requirement，决定本组走"一次过审"还是"先故意留一个可发现缺陷"（供交叉审核环节使用）；在任务单登记决策理由。
**【教学方法】** 决策谈话（双元制典型环节）。
**【设计意图】** 让"需求质量决定草稿质量"在决策点被显式感知；登记决策理由训练留痕习惯（对应审批工作流文化）。

### 第 4 步：实施（90 分钟）

#### 4.1 调用 Agent 生成草稿并解读 JSON（约 25 分钟）

```bash
# A 角（提单员）以标准化需求调用 ETL 编排 Agent
curl -s -X POST "$GW/api/v1/etl/agent/drafts" \
  -H "Authorization: Bearer $DAP_TOKEN" -H "Content-Type: application/json" \
  -d '{
        "requirement": "每日08:00汇总昨日售后工单，按门店与品类统计工单量与完结率，写入售后域DWS层，并监控order_id空值率",
        "domain": "after_sale"
      }' | jq '.draft_id, .status'
# 预期输出：2213 / "pending_approval"
```

生成的任务定义 JSON（板书核对四要素）：

```json
{
  "draft_id": 2213,
  "target_table": "dws_after_sale_order_day",
  "sql_script": "INSERT INTO dws_after_sale_order_day (dt, store_id, category, ticket_cnt, done_rate) SELECT dt, store_id, category, COUNT(*) AS ticket_cnt, SUM(CASE WHEN status='DONE' THEN 1 ELSE 0 END)/COUNT(*) AS done_rate FROM ods_after_sale_tickets WHERE dt = CURRENT_DATE - INTERVAL 1 DAY GROUP BY dt, store_id, category",
  "dag": { "cron": "0 8 * * *", "upstream_tasks": ["ods_after_sale_sync"] },
  "quality_rules": [
    { "type": "null_rate", "column": "order_id", "threshold": 0.01 },
    { "type": "row_count_delta", "baseline": "7d_avg", "threshold": 0.3 }
  ],
  "status": "pending_approval"
}
```

#### 4.2 人审界面走查：etl_drafts → approve（约 20 分钟）

```sql
-- 课程只读副本观察状态流转与留痕
SELECT id, target_table, status, created_by, reviewed_by, reviewed_at
FROM etl_drafts WHERE domain = 'after_sale' ORDER BY id DESC LIMIT 5;
-- 预期状态序列：pending_approval → approved（或 rejected + 理由）
```

```text
   id  | target_table              | status           | created_by | reviewed_by
------+---------------------------+------------------+------------+-------------
 2213 | dws_after_sale_order_day  | pending_approval | stu_1024   |
 1907 | dws_after_sale_ticket_7d  | approved         | stu_0902   | reviewer_01
```

```bash
# B 角（审核工程师）批准，走查三件事：留痕、只审不执行、驳回可回环
curl -s -X POST "$GW/api/v1/etl/drafts/2213/approve" \
  -H "Authorization: Bearer $REVIEWER_TOKEN" \
  -d '{"comment": "字段口径与需求一致，上游08:05才产出改为0 9 * * *，其余通过"}' | jq '.status'
```

走查记录三问：① Agent 有没有任何直连执行入口？（无）② reviewed_by/reviewed_at 是否落库？③ 驳回后草稿能否改后重提？

#### 4.3 双案例对照实验：价值边界量化（约 25 分钟）

```bash
# 案例 A：标准化需求（售后日报）→ Agent 草稿
# 案例 B：复杂需求（跨域回填+缓慢渐变维）→ 同一 Agent 草稿
# 用 git diff 行数量化人工修正成本
git diff --stat main -- etl/after_sale/draft_2213.sql   # 案例 A
git diff --stat main -- etl/finance/draft_2215.sql      # 案例 B
# 典型实测：A ≈ 0–5 行（改个 cron）；B > 60 行（口径重写）
```

各组把 diff 行数填入对照表，得出自己的结论并与预设命题对照：**标准化需求近直用，复杂需求好起点**——Agent 的价值是"消灭从零开始的空白页"，不是"消灭工程师"。

#### 4.4 为自己的售后域提交一个草稿（约 20 分钟）

```bash
# 定稿 requirement → 生成 → 导出入课程分支
curl -s -X POST "$GW/api/v1/etl/agent/drafts" \
  -H "Authorization: Bearer $DAP_TOKEN" -H "Content-Type: application/json" \
  -d @etl/after_sale/req_<学号>.json > etl/after_sale/draft_<学号>.json
git checkout -b feat/etl-draft-<学号>
git add etl/after_sale/ && git commit -m "feat(etl): 售后域草稿-<需求一句话>"
```

要求：JSON 中至少附 2 条质量规则（空值率/行数波动等五类任选），DAG 必须写明 upstream_tasks 并附拓扑说明一行。

#### 实施环节常见故障与应对

| 现象 | 原因 | 处置 |
|---|---|---|
| Agent 推荐了不存在的源表 | 需求用了同义异名词（"工单"vs"售后单"） | requirement 中补表名提示后重试 |
| 生成的 cron 早于上游产出 | Agent 不掌握上游时刻表 | 人工改 cron 并在审核意见注明 |
| quality_rules 为空 | 需求未写监控项 | 补齐四要素中"监控项"再生成 |
| approve 报 403 | 用了提单账号而非评审账号 | 切换 REVIEWER_TOKEN（权限分离演示点） |

### 第 5 步：检查（40 分钟）

**【教师活动】** 出示"检查基准"：审核清单六问＋DAG 拓扑正确性＋质量规则可执行性；组织组间交叉审核（A 组审 B 组草稿，互换角色再一轮）。
**【学生活动】** 按清单互审：逐字段核对表名与字段是否存在（查元数据表）、聚合粒度与需求是否一致、cron 是否晚于上游产出、quality_rules 是否覆盖需求中点名的监控项；产出"批准/驳回＋理由"交叉审核单。
**【教学方法】** 交叉检验＋核查表法。
**【设计意图】** 评价层级的目标在"检查"中落地：学生用自建的尺子量别人的作品，比教师打分更深刻地内化审核标准；驳回理由必须可执行（指到字段、给到改法）。

### 第 6 步：评价＋学生讲堂（30 分钟）

**【教师活动】** 主持学生讲堂⑤：随机抽 2 组，每组 5 分钟讲"Agent 只建议不执行"；按互评量表（讲清了吗/例子硬吗/结论立得住吗）组织同伴打分；最后 10 分钟总结 LF5 上半场并预告 L14（草稿里的 INSERT 为什么必然进审批工作流＝L4 护栏）。
**【学生活动】** 被抽组用"生成—审批—执行"三权分立图讲解；听众每人写一条"我听懂的一个点＋我还存疑的一个点"投入反馈箱；完成自评互评。
**【教学方法】** 费曼讲堂＋同伴互评。
**【设计意图】** "只建议不执行"是 LF5 的价值观锚点：责任归属（谁签字谁负责）、审计留痕（可回溯）、信任边界（生成≠可信）三句话必须能在讲台上说出来，才算达成评价层级。

## 八、评价设计（任务单评分表）

| 维度 | 权重 | 评分标准（满分按档：优 90+/良 75+/中 60+/差 <60） |
|---|---|---|
| 链路与字段解读 | 15% | 能不看资料复述五步链路与 JSON 四要素语义；抽查字段解释正确 |
| 草稿生成与核查 | 25% | 成功生成草稿；对照元数据定位≥1 处真实问题并给出修正 |
| 价值边界论证 | 20% | 双案例 diff 数据完整，结论"近直用/好起点"有量化支撑，不喊口号 |
| 审核意见质量 | 20% | 批准/驳回有理由，理由可执行（指到字段、给到改法），留痕完整 |
| 本组草稿 PR | 20% | 四要素齐、规则≥2 条、拓扑正确、描述如实（含 diff 行数） |

## 九、课后费曼任务

- **讲给谁**：同组同学或室友（最好非本专业）。
- **讲什么**："Agent 只建议不执行"——用你今天的双案例讲清三件事：① Agent 生成的是什么（建议/初稿）；② 为什么它不能自己执行（INSERT 进 L4 审批、责任归属、留痕）；③ 什么时候信它多点、什么时候信它少点（你的 diff 数据）。
- **自评三问**：① 我有没有用"从零开始 vs 改初稿"的对比让对方听懂价值？② 对方能不能复述出"谁签字谁负责"？③ 我有没有把"Agent 很聪明"讲成"Agent 全可靠"？（讲成了=没讲清）
