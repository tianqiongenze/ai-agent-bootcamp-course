## 三、学习目标

1. 【理解】画出本项目测试金字塔（单元 67 → 契约/护栏 → E2E 7 → 压测/评测）并说明各层职责、数量配比与执行成本的反比关系。
2. 【应用】运行 pytest＋覆盖率门禁与 Playwright 无头 E2E，从报告定位失败用例所属层与修复责任。
3. 【分析】判读 k6 阶梯压测报告：p95 延迟、错误率 2.4% 的构成、RPS 拐点档位，并写出一句瓶颈结论。
4. 【评价】用统计视角评判评测证据：论证"12 题 100% 为何没有统计意义"，说明 24 题＋held-out 12＋bootstrap 95% CI 的必要性。
5. 【评价】论证覆盖率门禁为何设 80%（项目实测 87%）：过高（凑数测试）与过低（回归裸奔）的代价权衡。

## 四、教学重点与难点

### 教学重点
1. 测试金字塔的成本—反馈结构：底层数量多跑得快（毫秒级）、顶层数量少贴近真实（分钟级），66+→7→1 的配比不是随意的。
2. k6 报告三要素判读法：p95（尾延迟比均值诚实）、错误率（2.4% 是谁的错——超时还是断言）、拐点（RPS 不再随 VU 增长的台阶）。

### 教学难点
1. **"12 题 100% 为何无统计意义"的统计直觉**——学生直觉是"全对还不说明问题？"
   - 突破策略：现场算概率——真实准确率 0.85 时 12/12 的概率约 14%，0.70 时仍有约 1.4%；再演示 bootstrap 重采样让置信区间"长出来"，直觉冲突被数据化解（教授方法学的通俗版）。
2. **覆盖率门禁的度**——为什么是 80 不是 100 也不是 50。
   - 突破策略：两个反例对照——100% 门禁催生"为覆盖而测"（断言空洞），50% 门禁下 L14 那类护栏函数可能整段裸奔；用"护栏模块必须 80+、胶水代码可豁免"的分级门禁收束讨论。

## 六、教学过程设计

### 第 1 步：资讯（30 分钟）

**【教师活动】** 白板画塔：单元 67（含 test_bindings 占位符绑定防线）→ 契约/护栏（L14 恶意单测归宿）→ E2E 7 条（Playwright 无头全链路）→ 压测与评测（k6 阶梯、24 题评测）；给出实测数字 67/7/300VU/2.4%，提问"如果只能保留一层，丢哪层最疼？"。
**【学生活动】** 对照dap-v2 的 tests/ 目录数一数各层文件数与金字塔是否吻合；把本学期自己提交过的 PR 归类到塔的某一层并贴名签。
**【教学方法】** 图示讲解＋目录考古。
**【设计意图】** 用学生自己的提交史锚定金字塔——"我的改动在哪一层被保护"比抽象分层更有代入感；丢层思想实验为后面门禁讨论埋线。

### 第 2 步：计划（30 分钟）

**【教师活动】** 发布"证据链任务单"：四站（单测覆盖率站/E2E 站/k6 判读站/评测统计站）各须产出一条可核验结论；给出 k6 判读三问模板与统计站实验步骤。
**【学生活动】** 排定小组四站的顺序与分工（建议底→顶顺序）；预填 k6 三问（p95 是多少/错误率构成/拐点在第几档 VU）的"预判值"；圈出自己本学期改动对应的单测缺口（为企业站 PR 备料）。
**【教学方法】** 站点式学习计划＋预测—验证。
**【设计意图】** 预填预判值延续 L14 的认知冲突法；提前圈单测缺口让企业站 PR 有明确靶子，避免"随便补两个测"。

### 第 3 步：决策（20 分钟）

**【教师活动】** 逐组确认：补测对象选哪个函数（优先护栏/绑定/缓存等共享模块，符合 TCG"共享包必测"）、预计覆盖增量；裁决争议（如"我的改动是 yaml，测什么？"→引导为"部署变更的冒烟脚本断言"）。
**【学生活动】** 定稿补测清单（2 个单测的目标函数与断言草案）；在任务单登记选择理由。
**【教学方法】** 决策谈话。
**【设计意图】** "yaml 改动测什么"是真实工程问题，公开裁决一次，全班受益；补测对象决策本身就是评价层级行为（判断什么值得测）。

### 第 4 步：实施（90 分钟）

#### 4.1 金字塔底座：单测＋覆盖率门禁（约 20 分钟）

```bash
pytest tests/ -q --cov=app --cov-report=term-missing --cov-fail-under=80
# 门禁 80%（TCG 铁律：共享包≥80、护栏/缓存等关键模块≥80）
# dap-v2 当前基线：67 测全绿，行覆盖 87%

pytest tests/test_bindings.py -q   # 占位符绑定防线：参数必须走绑定而非拼接
```

读报告两个动作：① 找出 `Missing` 列里最长的连续行段（最值得补的缺口）；② 区分"没测到的逻辑"与"测了但断言空洞"（后者更危险）。

#### 4.2 中层：E2E 7 条与冒烟 9 项（约 15 分钟）

```bash
npx playwright test e2e/ --reporter=line   # 7 条无头全链路（登录→提问→出数→图表）
make smoke                                 # 9 项冒烟（健康/查数/直答/备份产物…）
```

判读：E2E 失败先问"哪一层背锅"——E2E 红而单测绿＝集成缝隙（环境/契约），两层都红＝逻辑缺陷；记录一条失败归因（若全绿，回放教师预置的失败视频）。

#### 4.3 顶层之一：k6 阶梯压测报告判读（约 25 分钟）

```bash
k6 run loadtest/staircase.js --summary-export=reports/k6-staircase.json
# 上一次全量实测：300VU 阶梯、26865 请求、峰值 ~140RPS、错误率 2.4%
```

三问判读（任务单必填）：
1. **p95 是多少？** 尾延迟代表最差的 5% 用户体验，比均值诚实；对照 SLA（如 p95<800ms）。
2. **错误率 2.4% 是谁的错？** 拆解构成：超时（资源层 L2 的 20s 掐断/连接池排队）还是断言失败；2.4%≠灾难，但要能说清来源。
3. **拐点在第几档 VU？** RPS 不再随 VU 增长、p95 陡增的台阶即容量拐点；140RPS 前后的那档就是单副本的诚实容量（呼应 L6 容量外推公式）。

产出：在报告 JSON 上圈出拐点档位，写一句瓶颈结论（如"缓存命中率下降后 DB 直查比例上升，p95 陡增"）。

#### 4.4 顶层之二：评测集方法学＋混沌回放（约 30 分钟）

（a）"12 题 100%"的统计脆弱性（教授方法学的通俗版）：

```python
# 若真实准确率 p=0.85，12 题全对的概率：
0.85 ** 12   # ≈ 0.142 —— 真实水平 85% 的系统有 14% 概率"看起来全对"
0.70 ** 12   # ≈ 0.014 —— 连 70% 的系统也可能偶发 12/12
# 结论：12/12 区分不了 0.70 与 0.85，"100%"不是证据
```

升级方案三件套：**24 题**（样本翻倍）＋**held-out 12**（评测题绝不进 few_shots/知识库，防背题）＋**bootstrap 95% CI**：

```bash
python scripts/eval_nl2sql.py --set heldout12 --bootstrap 10000
# 输出：acc=0.875，bootstrap 95% CI [0.71, 0.96]
# 报告口径：必须带区间，"87.5%"单独出现即不诚实
```

（b）混沌降级回放（Redis 故障注入时间线）：

```
T+0    注入：课程环境断开 dap-cache 连接（故障注入脚本）
T+2s   主链直穿：/api/nl2sql 仍返回 200，响应头 degraded:true、cache_hit:false
T+8s   p95 短暂抬升（全部流量落到 DB）——对照 4.3 的拐点解释
T+90s  Redis 恢复 → 缓存命中回升、degraded 消失（自愈回归）
```

契约要求（DPC 铁律）：**每条降级路径必须有测试证明它会被触发且行为正确**——混沌回放就是那条测试的现场版；"降级没崩"和"降级被测过"是两回事。

### 第 5 步：检查（40 分钟）

**【教师活动】** 组织"证据链互审"：相邻组交换四站结论，逐条核对是否"可核验"（有命令、有数字、有出处）；抽查 2 组重跑对方的 k6 判读与 bootstrap 数字。
**【学生活动】** 互审打勾/打叉：p95 有没有写具体毫秒？错误率有没有拆构成？拐点有没有指认档位？评测结论有没有带置信区间？覆盖率结论有没有区分"没测"与"空测"？修补被打叉项。
**【教学方法】** 同伴互审＋证据核查。
**【设计意图】** "可核验"是 L16 发布决策的前置训练——不可核验的结论在门禁评审会上等于没有；互审清单直接复用 HSA（诚实自评）文化的操作化标准。

### 第 6 步：评价＋学生讲堂（30 分钟）

**【教师活动】** 主持学生讲堂⑥：抽 2 组各 5 分钟讲一份 k6 报告（三要素齐全为及格线）；10 分钟总结证据链全景并抛出 L16 引子——"证据齐了，谁有权按下上线按钮？"；布置费曼任务与岗位视角（测试开发工程师的一天）。
**【学生活动】** 讲堂主讲＋同伴按"三要素/一句话结论/诚实度"互评；每人写一句"我今天修正的一个直觉"（如"全对≠正确""均值会骗人"）投入反馈箱。
**【教学方法】** 费曼讲堂＋概念变更自述。
**【设计意图】** 统计直觉的修正是本讲最难的认知成果，用"修正了什么直觉"显性化；讲堂与 L16 答辩的"讲证据"能力同构，提前彩排。
